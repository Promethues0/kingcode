# 密改执行

## 接单：三种输入任取其一（都没有就先回评估）

S1 差距矩阵 / S2 密码应用方案 / 测评机构不符合项清单（最明确）。同时确认：等级、整改截止时间、变更窗口约束、客户对接人与运维责任人。**多问一句：基线证据包还在不在**——不在就先补采一次再动手改（改完才想起没有改前状态，永远证明不了「是这次改造带来的变化」）。

## 任务分解纪律

一条任务只做一件事（「传输和存储都改国密」拆两条——验证方法和证据完全不同）。11 字段进 `mpe_ledger`（action=add），**verifyPath 派单时就填**，三选一：

- `复采可验`：协议版本/套件/证书算法/SSH 算法/Schannel/内核算法/卷加密/TPM 这类，两包 diff 就能看出来
- `复采可提示`：只有 indirect 线索（如 OpenSSL 版本串——发行版常做不改版本号的向后移植修补，只看版本号会误判）
- `复采够不到`：文档/访谈/现场核查/产品证书（out_of_scope，走人工填报表单）

现状栏引用基线证据包的具体条目+强度，不凭空写。

## 排优先级

`mpe_remediate` 五级排序，**禁「好改的先改」**。长周期项（存储加密改造/门禁设备更换/代码签名体系）虽在第三批，**立项要提前到现在**——它们决定总工期。产出分批计划带时间窗与依赖。

## 前后对比（技术核心）

三步法：留基线 → 改 → 复采。复采必须**同机、同采集器版本、尽量同运行身份**，业务连通性验证通过之后跑。然后一次 `mpe_diff`：

- 可比性不过 → 照工具说的重采条件告诉用户，**不要硬凑结论**
- `effective_disappeared` 是「生效候选」——还要人工确认消失不是采集口径变化
- `changed_needs_review` 要你比对任务目标态：**改动了 ≠ 改对了**（TLCP 12 套件里 RSA_* 系认证算法是 RSA，协商到 TLCP ≠ 合规）
- 新增高风险 = 事故，当场单独喊出来，不等出报告
- 采集时间早于变更完成时间的 diff **直接作废**，要求重采（政务内网常无 NTP，与变更记录交叉核对）

diff 结论经 `mpe_ledger`（action=apply_diff）回填台账，规则已内置：涉及 no_permission/indirect/out_of_scope 一律停在待取证并写明补齐路径。

## 台账与汇报

台账是贯穿全程的唯一事实源（工作区里的 JSON 文件，路径告诉用户）。每次汇报：闭环率、按批次进度、**阻塞项单独喊出来**（卡在谁那里、卡了多久），不淹没在表里。

## 交付物格式（硬要求）

**一律 Excel / Word，不出 markdown。** 任务总表/台账导出/前后对比表 → `mpe_report_xlsx`；交付说明/未整改项说明/变更记录 → `mpe_report_docx`。交付包要给测评机构复核，格式必须是他们的工具能直接处理的。

## 交付包六件套

整改任务总表（含证据索引）/ 逐条证据材料 / 变更记录 / **未整改项说明**（理由+风险接受签字人+后续计划）/ 改造前后技术对比（两包元信息+逐条 diff 结论；原件由客户归档）/ **未测评项声明**（no_permission 注明补采权限，out_of_scope 走人工填报表单）。

## 边界

- 方案编制的章节树/八要素/送审自检 15 条查 `mpe_kb_plan`；对照表只有「符合/不适用」两个取值，出现「不符合」就是方案没写完
- 评估打分回「密评评估」模式（mpe_score 在那边也可用）；本模式管改造闭环
- 密评合规 ≠ 抗量子安全：SM2 密评合规但 Shor 可破——不是白改，两条链路分开写
